## 一、先把背景说清（不假设读者记得细节）

### 1.1 我们在优化什么

全文检索里有一类很常见的查询形态：

```
"solar +panel rebates"
   ^^^^^^  ^^^^^   ^^^^^^^
   加分项   必须命中  加分项
```

用户搜「太阳能板返利」：文档**必须**含 `panel`（否则不相关），含 `solar` 或 `rebates` 的**额外加分**。英文检索界叫它
required + optional（必选 + 可选），内部代号 IU（intersection_union）。它夹在两种极端之间：

- 纯 AND（全部必须命中）：太严；
- 纯 OR（命中任一即可）：太松；
- IU = 「有一个必选条款的 OR」。

### 1.2 我们拿什么当尺子

一台机器、同一个 Wikipedia 索引、同一批 943 条查询（业界公开的 Search Benchmark Game 查询集）、单核、多轮取最小值。
这 943 条里，**40 条**是上面这种 IU 形态——它们就是我们这条线的主战场。

### 1.3 一句话概念：「地板」（floor）

搜「前 10 名」时，堆里第 10 名的分数就是**地板**：任何分数够不到地板的文档都不必再算。
地板是**动态上升**的——越早搜到高分文档，后面的剪枝越狠。整条优化线就是围绕「如何更早、更准地用上这个地板」展开的。

### 1.4 IU 查询的生命周期（理解后面所有决策的关键）

同一个查询，在扫描过程中会**换性质**：

```
                 地板（第 10 名分数）
                   ▲
   阶段 A          │        阶段 B
   「必选自己就够」  │        「必选单独活不下去」
                   │
   MUST=panel       │        地板升过了 panel 的全局最高可能分
   (26,679 篇)      │        → panel 单独再也进不了前 10
   候选多但都好算    │        → 稀有的 rebates 事实上变成必选
                   │        → 查询退化成「求交集」
```

**这两个阶段由两个不同的引擎服务**，这也是本分支结构复杂的总根源：

| 阶段 | 现役引擎 | 特点 |
|---|---|---|
| A（地板低） | `iu_tight` 内核 | MUST 块驱动 + 一次性批量解所有 SHOULD（本轮已把归并换成 main 的 `merge_optional_freqs`） |
| B（地板高） | `promoted()`：把稀有 SHOULD 提升为必选 | **手写的逐文档 seek 交集——本文决策项 A 要动它** |

### 1.5 一个关键的「门槛」（决定每条查询走哪条路）

内核只在**必选比可选贵得多**时才接管，门槛写死在代码里：

```
最稀有的加分项 df × 3  <  必选项 df      → 进内核（阶段 A/B）
否则                                    → 走通用回落路径
```

为什么要有它：如果必选和可选一样便宜，用通用路径（`ReqOptScorer` + `TermLeafScorer` + 窗口 drain）反而更快；
如果必选稠密、加分项稀有，内核的「批量解加分项 + 提升」才有优势。

**实测这套门槛把 40 条 IU 查询正好切成两半**（用 main 二进制逐词量真实 df 得到的分类，全部 107 个词）：

| 路径 | 条数 | 例子（格式：最稀有加分项 → 必选项，倍数） |
|---|---|---|
| 内核（含阶段 B 的提升） | 20 | `solar +panel rebates`（rebates **362** 篇 → panel 26,679，**73.7 倍**）；`wildfire +risk maps`（1,387 → 43,239，31.2 倍）；`+electric grid stability`（12,750 → 44,752，**3.5 倍，贴着门槛**） |
| 通用回落路径 | 20 | `electric +vehicles`（44,752 → 36,751，**1.2 倍，过不了门槛**）；`+global markets`（29,141 → 56,628）；`urban +planning`（66,740 → 56,033）；`school +safety`（474,769 → 55,646） |
| K≥2 必选项 | **0** | 943 条基准里一条都没有 |

> **顺带纠正历史文档的一个错误**：`iu-framework-simplification.md` §4(a) 把
> `+global markets`、`electric +vehicles` 列为「提升后交集」的优化目标——但实测这两条
> **根本过不了 3 倍门槛**（比值 1.94x / 0.82x），压根不进提升路径。该文档别处已经引用了
> 3 倍门槛常量，属于**没有核对 df** 的笔误。

### 1.6 五条最差查询分别在哪条路上

> 下面的排名与倍数来自**历史记录口径**（`iu-framework-simplification.md` §0 记该分支当时最坏 2.39x、
> 4–5 条停在 2.0–2.4x；具体五条的 2.0–2.8x 数字出自更早一次会话记录），**不是本轮实测**。

| 最差查询（历史约 2.0–2.8 倍于 Lucene） | 所在路径 |
|---|---|
| `solar +panel rebates` | 内核 + 提升（阶段 B） |
| `wildfire +risk maps` | 内核 + 提升 |
| `+electric grid stability`（3.5 倍，贴门槛） | 内核 |
| `electric +vehicles` | **通用回落** |
| `+global markets` | **通用回落** |

**由此得到的判断（推理，非实测）：两条线各自覆盖一部分最差查询，不能只做一头。**

## 二、决策项 A：把「提升后的交集」从手写改成复用 main 的块级求交

### A.1 前因（这个东西为什么存在）

阶段 B 一旦开始，MUST 和「被提升的稀有 SHOULD」都变成必选，本质是**求交集**。求交集对 main 来说不是新问题——
`and_bulk_search` 早就有一套**块级 SIMD 求交**：一次解码一整块（128 篇），块内用 128-bit 指令
（`_mm_loadu_si128`，一轮对 4 个文档 id）做比对，循环推进。但我们这段是**手写的逐文档跳转版**：

```
main 已有的求交:   一次解一块 → 块内向量化比对 → 存活者算分
我们 promoted():   一个文档一个文档地 seek 必选项 → 慢，且与别处的交集实现重复
```

历史文档把 `promoted` 称为「裸 PostingIterator 上**第三个 leapfrog 副本**」（该「第三份」是历史文档的
口径；按代码清点，明确的逐文档 seek 交集是 `wand.rs` 的 classic AND 与这里的 `promoted` 两处，
把 `compound.rs` 里的 `ReqOptScorer::position_intersection` 也算上则更多——要点是它与这些实现重复），
并把它列为四个可简化点里**唯一「减代码 + 可能提性能」**的一项。

### A.2 用户场景（为什么它影响真实体验）

以 `solar +panel rebates` 为例，完整走一遍：

1. 用户搜「太阳能板返利」，前几毫秒：`panel` 命中 26,679 篇，`rebates` 只有 **362 篇**——但 rebates 太稀有，
   含它的文档 idf 极高，分数很突出。
2. 前 10 名很快被「既含 panel 又含 rebates」的高分文档占满，**地板抬升**。
3. 此刻 `panel` 单独的最高可能分已经低于地板 → 内核把 `rebates` 提升为必选，进入阶段 B。
4. **现在**：对每一个含 rebates 的文档（只有 362 个），代码逐个去 seek `panel` 和其他必选项。
   目标形态：这两个必选项各解一块，向量化比对，一次解决上百个候选。

对用户的观感就是：这类「常见词 + 稀有词」的搜索**慢一个档**，也正是历史上停在 2 倍多的那批。

### A.3 两种做法（要选一个）

| 路线 | 做法 | 优点 | 代价/陷阱 |
|---|---|---|---|
| **A1 历史方案** | 把 (MUST, 提升项) 打包成 main 的 AND 查询，交给 `and_bulk_search` | 直接复用 main 最快的 2 子句路径，IU 代码最薄 | 要**改 main 的 `Wand`**：① 它把 threshold 硬置 0、没有公开的设置口（只有 `pub(crate) with_shared_threshold` 能注入**跨游标共享**的地板，设不了游标自己的）→ 我们手里的地板传不进去；② 它对文档已耗尽的 posting 直接跳过 → 1+1 的 AND 会退化成「只查 MUST」= **结果错**，必须额外守卫 |
| **A2 块原语方案（我推荐）** | 在 `promoted()` 内部自己写块循环：`take_docs_one_block_upto` 取块 + main 的 `intersection::intersect` 求交 + main 的 `merge_optional_freqs` 给剩余加分项批量取频率 | **不动 main**（已核实这三个原语在 main 上的可见性足够直接调用）；地板仍在自己手里；不走 `Wand::new` 的构造路径，**据结构推断**不会触发陷阱②（仍需测试钉住） | IU 代码里多一个块循环（约 60–80 行替换现有约 45 行）；两个原语签名不匹配（`intersect` 收 `&[u32]`，取块出来的是 `(u64, u32)` 对），需要自己抽一列 |

### A.4 怎么验证、风险多大

- **验证**：943 条 dump 与社区 main 逐字节比对（块求交后只要仍按文档序、必选项按计划序累加分数，就能保位一致）；
  再加 IU 40 条 + 全量 943 计时。
- **预期与风险（待实测，勿当结论）**：块级求交对「必选项块内候选多」的情形应该更有利；但门槛只保证必选项
  至少是最稀有加分项的 3 倍频——贴着门槛的那几条（`+electric grid stability` 3.5 倍，必选项 44,752 篇）
  收益可能有限，而 73.7 倍那条（必选 26,679 篇）空间更大。**实际收益必须 A/B 测**，不要在决策前当成已成立。
- **建议**：做，走 A2；把它当作一次「性能重构 + 复用 main 原语」，用 dump 位一致 + bench 判定成败。

## 三、决策项 B：两个「从没量过」的机制，各做一次消融实验

「消融实验」= 把某个机制临时关掉，重建一个二进制，对比计时。一次约 25 分钟（构建 20 + 跑 2）。

| 消融对象 | 前因（它为什么可疑） | 对什么查询有用 | 可能的结论 |
|---|---|---|---|
| **3 倍门槛** | 它把 40 条查询正好切两半；`+electric grid stability`（3.5 倍）、`+financial reporting standards`（3.8 倍）**贴在门槛线上**——阈值稍微变动，它们就在两条路径间搬家 | 所有「必选和加分项频率接近」的查询。两条路径都已证明各有价值，所以换阈值有双向空间 | 找到更好的阈值；或证明现有 3 倍合理。**两种结果都能写进 PR，作为这个常量的依据** |
| **逐候选地板预检**（**我在修 lint 时加的**，不是为性能加的） | 当初加它只是为了「让 floor 参数有实际用途、消除编译警告」——和之前被删的 `sticky_floor` 是同一类问题：**动机不纯、无实测**。现在每个候选都要多付一次 f64 求和 | 所有内核查询的每候选成本 | 如果地板预检几乎从不触发（因为用的是全局上界、很松），就该删掉，省掉每候选的开销 |

**已撤回的一项**：原计划里还有「TermLeafScorer 消融」。查到历史提交 `c68f74947` 自带实测
（IU 40 条 335.3ms → 189.3ms，**−43.5%**），有数据背书，**不消融、不删**。

## 八、决策记录

### 决策项 A —— **不做**（2026-10-04）

`promoted()` 保持现有独立实现，A1/A2 均不执行。

- **理由**：真正重复的只是那几十行「逐文档求交」，冗余量不大；留成独立一份反而更清晰、更好读。
  A1 只覆盖 3/20 条（纯 2 子句 AND 形态）却要改 main 最热的 AND 引擎；A2 生产行数持平、不减代码。
- **代价与接受**：社区评审可能仍会指出「这是第 4 处交集实现」。若被问到，按实测口径回答：
  它的重复面是 ~87 行编排、且服务于 IU 的专属语义（提升后仍要加可选分），与纯 AND 引擎不同。
- **条件性重访**：① K≥2 混合形状成为真实负载；② 社区明确要求消除该处交集 → 再评估 A1++
  （把 AND 引擎改造成可暴露块候选的形态，属独立接口设计，不在本 PR）。

### 与本决策连带的 hardening（AND 丢弃耗尽子句）

- 该修**原本是 A1 的前置**（A1 会是第一个传「已推进过的 posting」进去的调用方）。A 取消后，
  **我们这条线不再需要它**。
- 但缺陷本身已由两方独立复现确认：`Wand::new`（`wand.rs:2576`）对已耗尽的合取项直接跳过，
  AND 会把交集按剩余子句计算 → **多返回文档**；语义为错，但**当前无可触发的生产路径**
  （loader 层已拦掉空 posting）→ 属「潜伏的 API footgun」。
- **处置**：不在本 PR 改动 main；作为「已核实的潜伏缺陷」记录在案。回归用例已备好
  （`/tmp/and_exhausted_test.rs.txt`，29 行，改 `Wand::new` 的 AND 分支 3–5 行即可转绿），
  将来若有人要动这块可顺手带上；是否单独对外提一句待定。

### 决策项 B —— **两个消融都做了，且第二个的结论被独立复核推翻并已改正**（2026-10-04）

方法（修正后）：`RUSTFLAGS='-C target-cpu=native'`，基线 = `origin/main`（`7b97db782`）——
注意 `wt-main` 停在更旧的 `637194173`，不能当基线。**消融变体必须与参照物同一代码状态**：
第一轮的门槛消融跑在「仍带逐候选预检」的代码上，把预检的开销错误归因给了门槛（见下）。

| 套件 | 基线 main | 最终分支 |
|---|---|---|
| IU 40q | 1005.9ms | **97.5ms（−90.3%）** |
| 全量 943 | 2620.4ms | **1701.1ms（−35.1%）** |
| 合成 12 | 75.7ms | **11.0ms（−85.5%）** |

**结论 1：逐候选地板预检是负优化 → 已删除**（`11465fb69`，+2/−70）。
收益全在内核查询上（`+housing market trends` −35%、`wildfire +risk maps` −33%、
`+electric grid stability` −31%、`solar +panel rebates` −30%），无真回归。删除后 multi
内核不再需要 `floor` 参数（无 promotion），K=1 内核保留 floor 仅供 promotion。

**结论 2（修正）：3x 门槛也是负优化 → 已删除**（`6a040245f`）。
初版消融的结论是「门槛过严但别删」——**错了**：那版消融的参照物 `c_native` 仍含预检，
把预检的每候选开销记到了门槛账上。在**最终代码**上重建门槛恒开变体后：

| 套件 | 最终分支 | 门槛恒开 | 变化 |
|---|---|---|---|
| IU 40q | 130.1ms | **96.6ms** | **−25.8%** |
| 全量 943 | 1749.2ms | 1696.1ms | −3.0% |
| 合成 12 | 10.8ms | 10.9ms | +0.6%（噪声） |

逐条 **29 快 / 11 慢**，最慢仅 +3%（在 IU40 自身 2.5–3.2% 的轮间离散度内）；原先被点名的
两个「输家」实为赢家（`+global markets` −19.8%、`urban +planning` −9.2%）。现路由只看
